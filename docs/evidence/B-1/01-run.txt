                       Qwen3-8B                          Qwen3-0.6B

  verdict (28 points)  24 noise, 4 real <2%, 0 >=2%      16 noise, 8 real <2%, 4 >=2%

The four 0.6B points beyond 2%: prefill c=8 +2.3%, prefill c=16 +2.8%, short c=8 +2.1%, short c=32 -3.2%.
Where Dynamo costs something: 0.6B short (128 in / 128 out) at c=32 and c=64, about 50 requests/s: throughput -3.2% and
-1.8%, and at c=64 TTFT p99 137 -> 304 ms, E2E p99 +12.5%. On 8B nothing measurable (TTFT p99 +39% at decode c=16 on
32 requests).

Reading of the TTFT difference (hypothesis, not measured): Dynamo's frontend tokenizes and detokenizes in Rust, while
vLLM's own API server does it in one Python process that queues as concurrency rises. Evidence for it: the gap grows with
concurrency, TPOT is equal, and when the engine is the bottleneck (8B prefill c=16: 2.3 s on both) the gap disappears,
so Dynamo is not just sending an early empty chunk. To confirm before quoting it: a profile of vLLM's API server at
c=32, or vLLM with --api-server-count > 1.

Not shown by this test: Dynamo's gains (KV-aware routing across workers, disaggregation, planner) need more than one GPU.
